# 보고서 자동 반영 운영

2026-09-17 운영자의 명시적 요청으로 실제 Firebase의 보고서 감시 설정을 `enabled=true`, `autoApply=true`로 전환했다.

## 처리 범위

`01_전담멘토링` 폴더와 하위 캠퍼스의 보고서를 읽고 필수 항목, 회사·캠퍼스·멘토·회차, 본문과 진행일을 검증한다. 회차 탭의 날짜가 유효하고 필수 항목이 모두 채워지면 첫 조회부터 지정 마스터의 완료 체크와 보고서 작성일을 반영한다. 시간 기반 안정화 대기는 제거했다. 작성일 필드가 있으면 그 날짜를 사용하고, 없으면 운영자 요청에 따라 탭 날짜를 작성일로 사용한다. 진행일·파일 수정 시각·자동 확인 시각으로 대체하지 않는다. 작성일 필드가 있으나 비어 있으면 보류한다.

- 완성 보고서만 처리하며 기존 체크는 중복 집계하지 않는다.
- 이름이 애매하거나 캠퍼스가 다른 경우, 중복 회차·수식·양식 불일치 등은 보류한다.
- 기존 XLSX의 A열 시작 양식과 B열 시작 양식을 지원한다. 보고서 근거 주소도 실제 위치를 기록한다.
- 멘토 이름의 말미 ‘멘토/멘토님’은 호칭으로 처리한다. 다른 사람의 이름은 허용하지 않는다.
- 대상 셀 미리보기, 원본 버전 확인, Firestore 실행 잠금, 반영 후 원본 재조회와 실행 이력을 사용한다.
- 파일명 자동 변경과 메일 발송은 이 백그라운드 작업에 포함하지 않는다.

## 백그라운드 실행

macOS 로그인 서비스 `kr.co.mysc.axpm.report-monitor`가 `scripts/report-monitor.ts`를 실행한다. 앱 개발 서버나 브라우저 없이 실제 Firebase/Google API에 연결한다. 파일 버전 체크포인트로 변경 없는 본문 조회를 생략하고 최근 변경 파일·실패 재시도 대상을 우선 처리한다. 한 번에 최대 15개, 본문 처리 예산 60초로 점검하고 60초 대기 후 다음 묶음을 처리한다(진행 중인 API 요청은 예산을 넘길 수 있음). 6시간마다 전체 대조한다. 조회 실패와 일시적 마스터 충돌은 1분부터 최대 15분까지 재시도 간격을 늘린다. 필수 필드 충족 후 별도 시간 대기는 없다. 변경 감지는 현재 폴링 방식이라 편집 즉시 푸시되는 구조는 아니다. 자세한 근거와 측정 계획은 [MYSCube 최적화 조사](MYSCUBE-OPTIMIZATION.md)를 참고한다.

서비스는 사용자 로그인 때 실행되며 종료 후 재시작된다. **이 Mac이 켜져 있고 사용자 로그인이 유지되어야 한다. 절전·전원 종료 중에는 실행되지 않는다. 클라우드 상시 서버 배포를 대신하는 것은 아니다.** ADC 인증이 만료되면 Google 재로그인이 필요하다.

상태는 Firebase `users/{uid}/automation/reportWorker`, 로그는 Git에서 제외된 `private/monitor/`에 저장된다. 캠퍼스 자동화 화면에 실행 상태와 최근 점검 시간이 표시된다.

```sh
# 설치 (이미 설치된 서비스는 중복 생성하지 않음)
npm run monitor:install -- ai@mysc.co.kr

# 상태 확인
launchctl print gui/$(id -u)/kr.co.mysc.axpm.report-monitor

# 서비스 중지 및 로그인 자동 실행 해제
launchctl bootout gui/$(id -u) "$HOME/Library/LaunchAgents/kr.co.mysc.axpm.report-monitor.plist"
```

앱에서 ‘필수 항목 검증을 통과한 보고서를 마스터에 자동 반영’을 끄고 설정을 저장하면 다음 점검부터 쓰기를 중지한다. ‘자동 점검 사용’을 끄면 예약 점검도 건너뛴다. 이미 진행 중인 요청을 되돌리는 기능은 아니다.

## 에이전트 활동 이력

홈·캠퍼스 자동화·작업 센터의 ‘에이전트 활동’에서 다음 기록을 확인할 수 있다.

- 실제 마스터 기록: 기업·회차, 실행 주체(`report-monitor`, `agent`, `operator`, `campus-automation`), 변경 셀과 전후 값, 보고서 근거, 처리 시각 및 검증 상태.
- 이미 완료된 건: ‘기존 기록 확인 · 변경 없음’. 새 셀 변경으로 집계하지 않는다.
- 자동 감시 한 묶음: 읽은 파일 수와 각 보고서의 필수 항목 보완·충돌·실패·반영 결과. 완료 시점별 기록을 별도로 보존한다.
- Hermes 등의 에이전트 요청: 요청 내용과 실제 응답·완료 상태.

최신 50개 활동을 30초마다 조회하며 실제 Drive 메타데이터 이력과 별도로 표시한다. 출처가 저장되기 전 기록은 ‘이전 실행 · 출처 미기록’으로 표시한다. 직접 실행으로 분류하지 않은 이전 이력의 주체를 추정하지 않는다.

이전 시간 기반 구현의 검증에서 모든컨설팅 1회차 보고서를 두 번 읽고 120초 이상 내용 유지와 원본 버전을 확인한 뒤, 마스터 7행 반영 경로를 실행했다. 기존 체크가 이미 있어 `cells=[]`였으며 Firestore에 `verified` 이력이 저장됐다. 이를 신규 셀 쓰기 성공으로 간주하지 않는다.

필수 필드 기반 이벤트는 `-fields-v2` 식별자로 기록한다. 과거 쓰기의 결과가 불확실하면 시트 내 반영 마커와 실제 셀이 모두 일치하는지 확인한 뒤 기존 이력을 검증 완료로 정리하며, 확인되지 않으면 새 쓰기를 보류한다. 체크가 있고 작성일만 비어 있는 회차는 날짜만 보충한다. 기존 날짜는 자동 덮어쓰지 않는다. 날짜 값이 맞지만 일반 숫자 형식이면 같은 공용 엔진에서 해당 날짜 셀의 표시 형식만 m/d로 보정한다.

## 반복 가능한 MCP / API 인터페이스

자동 워커, HTTP API, Hermes MCP는 모두 `runReportWatch`를 사용한다. 기업명·행 번호·테스트 파일 ID를 운영 로직에 고정하지 않는다. 감시 설정의 폴더에서 파일을 발견하고, 본문 기업·캠퍼스·멘토를 마스터에 매칭해 대상 행과 회차 열을 결정한다.

- MCP `axpm_scan_report_submissions({fileId?})`: 원본 재조회 및 미리보기. 시트 쓰기 없음.
- MCP `axpm_apply_report_submissions({fileId?})`: 자동 반영 설정 확인 후 같은 엔진으로 검증·쓰기·재조회.
- `fileId` 생략: 변경 파일 큐 한 묶음 처리. `fileId` 지정: 감시 폴더에 포함된 파일만 강제 재검증. 폴더 밖 파일은 거부.
- HTTP `POST /api/automation/reports/run`: `{fileId?, mode:"preview"|"apply"}`. 기존 Firebase 인증 및 권한 정책 유지.
- `axpm_inspect_report_watch`와 `axpm_master`로 결과를 다시 조회한다. 자동 활동 원장은 변경 셀·근거·전후 값을 보존한다.

CLI도 등록된 MCP 도구를 호출한다. 별도 일회용 셀 쓰기 코드가 아니다. in-memory MCP 전송을 사용하지만 Firebase와 Sheets API는 실제 연결이다. Hermes의 HTTP MCP 배포 가용성을 검증하는 명령은 아니다.

```sh
# 기본은 미리보기, --file 생략 시 관리 폴더의 변경 보고서 묶음
npm run sync:reports -- --email <허용된-운영자-이메일> --file <보고서-ID>

# 실제 반영 후 동일 도구를 재호출해 중복 방지 확인
npm run sync:reports -- --email <허용된-운영자-이메일> --file <보고서-ID> --apply --repeat
```

에이전트 예시: “이 보고서 URL을 읽고 필수 필드와 회차 날짜를 확인해 마스터에 반영해줘. 같은 도구로 재검증하고 변경 셀과 활동 이력을 보고해줘.”

2026-09-17 디자인워커스 4회차 실제 검증: 기존 X48 쓰기를 시트 반영 마커와 실제 값으로 확인하고, 공용 엔진이 빈 Y48 작성일에 2026-09-17을 기록했다. N48 원본 수식은 4, K106 전체 전담 집계는 212이며 기존 수식을 수정하지 않았다. 이력은 `report-monitor` 주체로 저장됐다.

등록 MCP 도구의 실제 연속 호출 검증: 동일 보고서에 `axpm_apply_report_submissions`를 두 번 호출해 두 실행 모두 1~4회차 `unchanged`를 확인했다. 본문 재조회와 검증을 생략하지 않으며 같은 회차를 추가 집계하지 않는다.

최종 표시 형식 보정도 MCP 공용 경로로 수행했다. 첫 호출은 Y48의 일반 숫자 표시를 날짜 형식으로 바꾼 뒤 원본 버전 변경 감지로 관찰 상태를 `uncertain`으로 남겼다. 즉시 이어진 같은 도구의 두 번째 호출은 원본을 새로 읽고 1~4회차 모두 `unchanged`를 반환했다. 별도 Sheets API 재조회와 Google Sheets 화면에서 Y48=`9/17`, X48=`TRUE`, N48=`4`, K106=`212`를 확인했다. 실제 셀 반영 이벤트는 모두 `verified`이며, 중간 점검의 오류 이력은 지우지 않았다.

최종 검증: 테스트 65개 통과, 타입 검사·프로덕션 빌드 통과. QA 중 일시 중지했던 자동 감시 설정은 `enabled=true`, `autoApply=true`로 복구하고 로그인 서비스를 최신 코드로 다시 시작했다.
